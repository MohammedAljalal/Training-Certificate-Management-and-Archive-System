## 1. Table: `users`

**Purpose:** Stores all user accounts for the system. Both Administrators and Participants share this table, distinguished by the `role` column. This design avoids duplication of authentication logic and mirrors the structural identity of the two roles (same attributes, same login mechanism).

**Engine:** InnoDB  
**Character Set:** utf8mb4  
**Collation:** utf8mb4_unicode_ci

| Column | SQL Type | Nullable | Default | Constraints | Description |
|---|---|---|---|---|---|
| `id` | `INT UNSIGNED` | NOT NULL | — | PRIMARY KEY, AUTO_INCREMENT | Surrogate primary key. Internal unique identifier for each user account. Never exposed in public-facing URLs or verification output. |
| `full_name` | `VARCHAR(100)` | NOT NULL | — | — | Full name of the user (administrator or participant). Required for all accounts (BR-21). Maximum 150 characters in business rules — 100 is sufficient for typical names; use 150 if requirement is interpreted strictly as a maximum storage limit. |
| `email` | `VARCHAR(255)` | NOT NULL | — | UNIQUE | Email address used for login and account identification. Must be unique across all users (administrators and participants) per BR-12 and NFR-31. Must follow RFC 5322 format (validated at application level). |
| `password` | `VARCHAR(255)` | NOT NULL | — | — | bcrypt hash of the user's password. Never stores plain text. Generated by `password_hash($plaintext, PASSWORD_BCRYPT)`. VARCHAR(255) accommodates current and future bcrypt hash lengths (bcrypt outputs 60 characters; 255 provides future-proofing). |
| `role` | `ENUM('admin','participant')` | NOT NULL | — | — | Role discriminator. Determines what the user may access. Only two values are permitted. Administrators manage the system; Participants have read-only self-service access to their own records. No default is set — role must be explicitly assigned at insert time. |
| `phone` | `VARCHAR(20)` | NULL | NULL | — | Optional phone number. No specific format enforced at database level. Application validates format if provided. |
| `date_of_birth` | `DATE` | NULL | NULL | — | Optional date of birth. If provided, application validates that it is a past date. Not exposed on public verification page (BR-16). |
| `status` | `ENUM('Active','Inactive')` | NOT NULL | `'Active'` | — | Account status. `Active` = can log in. `Inactive` = login blocked (soft-deleted participant). Set to `Inactive` when a participant has issued certificates and an administrator requests deletion (BR-10 tier 1) or as an alternative when deletion is blocked (BR-10 tier 2). Administrators are never set to `Inactive` through the application UI. |
| `created_at` | `TIMESTAMP` | NOT NULL | `CURRENT_TIMESTAMP` | — | Record creation timestamp. Set automatically by the database at INSERT time. Used for registration date display (FR-20). |
| `updated_at` | `TIMESTAMP` | NOT NULL | `CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` | — | Last modification timestamp. Updated automatically by the database whenever the row is modified. |

**Primary Key:** `id`  
**Unique Keys:** `email`  
**Indexes:** `email` (implicit from UNIQUE), `role` (additional INDEX for filtering), `status` (additional INDEX for filtering)

**Business Rules Enforced by this Table:**
- BR-12: UNIQUE on `email`
- BR-20: `password` column stores only hashes; enforced at application level
- BR-21: `full_name` NOT NULL
- NFR-31: UNIQUE constraint on `users.email`

## 2. Table: `courses`

**Purpose:** Stores all training course records. Administrators create, edit, and optionally deactivate courses. A course cannot be deleted once it has associated enrollments.

**Engine:** InnoDB  
**Character Set:** utf8mb4  
**Collation:** utf8mb4_unicode_ci

| Column | SQL Type | Nullable | Default | Constraints | Description |
|---|---|---|---|---|---|
| `id` | `INT UNSIGNED` | NOT NULL | — | PRIMARY KEY, AUTO_INCREMENT | Surrogate primary key. Unique identifier for each course. |
| `title` | `VARCHAR(255)` | NOT NULL | — | — | Course title. Required, between 3 and 255 characters (BR-19). The minimum length (3 chars) is enforced at the application level; the database enforces NOT NULL and the VARCHAR length cap. |
| `description` | `TEXT` | NULL | NULL | — | Optional course description. Maximum 2000 characters enforced at application level (FR-15). TEXT type accommodates longer descriptions without padding waste. |
| `start_date` | `DATE` | NOT NULL | — | — | The official start date of the course. Used in enrollment completion date validation (BR-05 condition 3). |
| `end_date` | `DATE` | NOT NULL | — | — | The official end date of the course. Must be on or after `start_date` (BR-18). Used in enrollment completion date validation (BR-05 condition 4). |
| `location` | `VARCHAR(255)` | NULL | NULL | — | Optional location string for the training venue. No geographic validation applied. |
| `status` | `ENUM('Active','Inactive')` | NOT NULL | `'Active'` | — | Course operational status. `Active` courses are displayed for enrollment. `Inactive` courses are still retained for historical reference. |
| `created_at` | `TIMESTAMP` | NOT NULL | `CURRENT_TIMESTAMP` | — | Record creation timestamp. |
| `updated_at` | `TIMESTAMP` | NOT NULL | `CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` | — | Last modification timestamp. |

**Primary Key:** `id`  
**Indexes:** `status` (additional INDEX for filtering active courses)

**Business Rules Enforced by this Table:**
- BR-11: Course deletion blocked when enrollments exist — enforced by `ON DELETE RESTRICT` FK on `enrollments.course_id`
- BR-18: `end_date >= start_date` — enforced at application level (server-side validation)
- BR-19: `title` NOT NULL, VARCHAR(255)

## 3. Table: `enrollments`

**Purpose:** Bridges users (participants) and courses in a many-to-many relationship. Each row represents one participant's enrollment in one course. Tracks status progression from Enrolled through Completed. This table is the central link in the data model — certificates reference enrollments, and participant deletion rules evaluate enrollment existence.

**Engine:** InnoDB  
**Character Set:** utf8mb4  
**Collation:** utf8mb4_unicode_ci

| Column | SQL Type | Nullable | Default | Constraints | Description |
|---|---|---|---|---|---|
| `id` | `INT UNSIGNED` | NOT NULL | — | PRIMARY KEY, AUTO_INCREMENT | Surrogate primary key for the enrollment record. |
| `user_id` | `INT UNSIGNED` | NOT NULL | — | FOREIGN KEY → `users.id` ON DELETE RESTRICT | The participant enrolled in the course. References `users.id`. Only users with `role = 'participant'` should be inserted here (enforced at application level, not database level). `ON DELETE RESTRICT` prevents participant hard-deletion when enrollment records exist (BR-10 tier 2). |
| `course_id` | `INT UNSIGNED` | NOT NULL | — | FOREIGN KEY → `courses.id` ON DELETE RESTRICT | The course the participant is enrolled in. `ON DELETE RESTRICT` prevents course deletion when enrollments exist (BR-11). |
| `status` | `ENUM('Enrolled','In Progress','Completed')` | NOT NULL | `'Enrolled'` | — | Current enrollment status. Allowed transitions: Enrolled → In Progress → Completed (FR-28). Status cannot be downgraded once a certificate has been issued (FR-30, enforced at application level). `Completed` status is required before certificate issuance (BR-02). |
| `completion_date` | `DATE` | NULL | NULL | — | The date the participant completed the course. Required (NOT NULL at application level) when `status` is set to `'Completed'` (FR-29). NULL for enrollments that are not yet completed. Must satisfy four validation conditions (BR-05): valid date, ≤ today, ≥ `courses.start_date`, ≤ `courses.end_date`. |
| `created_at` | `TIMESTAMP` | NOT NULL | `CURRENT_TIMESTAMP` | — | Record creation timestamp (enrollment date). |
| `updated_at` | `TIMESTAMP` | NOT NULL | `CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` | — | Last modification timestamp (last status update). |

**Primary Key:** `id`  
**Foreign Keys:**
- `user_id` → `users.id` ON DELETE RESTRICT ON UPDATE CASCADE
- `course_id` → `courses.id` ON DELETE RESTRICT ON UPDATE CASCADE

**Unique Keys:** `(user_id, course_id)` — composite unique constraint (BR-01, NFR-27)

**Indexes:**
- `(user_id, course_id)` implicit from UNIQUE
- `user_id` implicit from FK (also supports participant profile queries)
- `course_id` implicit from FK (also supports course detail queries)
- `status` — additional INDEX for filtering

**Business Rules Enforced by this Table:**
- BR-01: UNIQUE `(user_id, course_id)` prevents duplicate enrollment
- BR-02: `status = 'Completed'` required — evaluated at application level before certificate issuance
- BR-10 tier 2: `ON DELETE RESTRICT` on `user_id` blocks participant hard-delete when enrollments exist
- BR-11: `ON DELETE RESTRICT` on `course_id` blocks course deletion when enrollments exist
- NFR-27: UNIQUE composite constraint

## 4. Table: `certificates`

**Purpose:** Stores all issued certificate records. Each certificate is linked one-to-one with a completed enrollment. Certificate records are permanent — they are never deleted, only revoked. The table supports the complete certificate lifecycle: issuance, validation, revocation, archiving, public search, and authenticated download.

**Engine:** InnoDB  
**Character Set:** utf8mb4  
**Collation:** utf8mb4_unicode_ci

| Column | SQL Type | Nullable | Default | Constraints | Description |
|---|---|---|---|---|---|
| `id` | `INT UNSIGNED` | NOT NULL | — | PRIMARY KEY, AUTO_INCREMENT | Surrogate primary key for the certificate record. |
| `enrollment_id` | `INT UNSIGNED` | NOT NULL | — | UNIQUE, FOREIGN KEY → `enrollments.id` ON DELETE RESTRICT | The enrollment this certificate was issued for. The UNIQUE constraint enforces one-certificate-per-enrollment (BR-03, NFR-26). `ON DELETE RESTRICT` ensures certificate records cannot be lost when parent records change (BR-09). |
| `certificate_number` | `VARCHAR(30)` | NOT NULL | — | UNIQUE | The human-readable, globally unique certificate identifier. Format: `CERT-YYYY-XXXXXXXX` (13 characters maximum; VARCHAR(30) provides safety margin). Generated using PHP `random_bytes()` before the database transaction begins. The UNIQUE constraint is the definitive uniqueness guarantee (BR-04, NFR-25). |
| `issued_at` | `DATE` | NOT NULL | — | — | The date the certificate was issued. Set to the current date at issuance time. Used in public verification display (FR-47). |
| `file_path` | `VARCHAR(500)` | NOT NULL | — | — | Server-side storage path to the generated PDF file (e.g. `storage/certificates/CERT-2026-ABCDEF12.pdf`). Stored as a relative path from the application root or as an absolute server path. This path is used by authenticated download controllers only. Never exposed directly to users or browsers. VARCHAR(500) accommodates deeply nested paths on some hosting environments. |
| `status` | `ENUM('Valid','Revoked')` | NOT NULL | `'Valid'` | — | Current certificate status. `Valid` = active certificate. `Revoked` = invalidated certificate, retained permanently in archive (BR-07). Set to `'Valid'` on creation; changed to `'Revoked'` only by administrator revocation action. |
| `revoked_at` | `TIMESTAMP` | NULL | NULL | — | Timestamp of revocation. NULL for `Valid` certificates. Set to current timestamp when status changes to `Revoked` (BR-07). |
| `revocation_reason` | `TEXT` | NULL | NULL | — | Mandatory reason text provided by administrator at the time of revocation. NULL for `Valid` certificates. Required to be non-empty when `status = 'Revoked'` (BR-07, FR-42); enforced at application level. |
| `created_at` | `TIMESTAMP` | NOT NULL | `CURRENT_TIMESTAMP` | — | Record creation timestamp. |
| `updated_at` | `TIMESTAMP` | NOT NULL | `CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP` | — | Last modification timestamp. |

**Primary Key:** `id`  
**Foreign Keys:**
- `enrollment_id` → `enrollments.id` ON DELETE RESTRICT ON UPDATE CASCADE

**Unique Keys:**
- `enrollment_id` — one certificate per enrollment
- `certificate_number` — globally unique certificate number

**Indexes:**
- `enrollment_id` implicit from UNIQUE FK
- `certificate_number` implicit from UNIQUE (supports public search by cert number)
- `status` — additional INDEX for archive filtering

**Business Rules Enforced by this Table:**
- BR-03: UNIQUE `enrollment_id` — one certificate per enrollment
- BR-04: UNIQUE `certificate_number` — global uniqueness
- BR-07: Revocation fields (`revoked_at`, `revocation_reason`, `status`) support revocation workflow; no DELETE permitted
- BR-09: `ON DELETE RESTRICT` on `enrollment_id` protects certificate records from cascading deletion
- NFR-25: UNIQUE on `certificate_number`
- NFR-26: UNIQUE on `enrollment_id`

## 7. Public Verification Query Design

The public verification page (FR-45–FR-52-PV) must expose only specific fields. The following column subset is the only data ever returned to unauthenticated visitors:

| Source Table | Column | Purpose on Verification Page |
|---|---|---|
| `certificates` | `certificate_number` | Display certificate ID |
| `users` | `full_name` | Display participant name |
| `courses` | `title` | Display course name |
| `enrollments` | `completion_date` | Display completion date |
| `certificates` | `issued_at` | Display issuance date |
| `certificates` | `status` | Display Valid/Revoked indicator |

**Columns explicitly excluded from public query:** `users.email`, `users.phone`, `users.date_of_birth`, `users.id`, `users.password`, `users.role`, `certificates.file_path`, `certificates.revocation_reason`.

The verification controller must use explicit column names (never `SELECT *`) and build the WHERE clause using prepared statements (BR-23, NFR-01).
